# Module System

Every UI panel, checklist, prompt, and quality evaluation in PoF is anchored to a **module** — a game-development domain such as `arpg-combat` or `materials`. Three static registries define what each module contains and what drives it at runtime. A fourth layer (the NBA engine) wires those registries together into actionable recommendations.

## How It Works

### 1. Identity — `SubModuleId` (`src/types/modules.ts:6–51`)

The canonical `SUB_MODULE_IDS` const array lists every module slug. The derived union type `SubModuleId = (typeof SUB_MODULE_IDS)[number]` is the single source of type identity across the codebase. Adding a new module requires adding its slug here first — the comment in the file (`ModuleSchema`) describes the five domains that must stay in sync: type identity, registry entry, feature graph, store key, and component factory.

### 2. Registry 1 — Sub-module definitions (`src/lib/module-registry.ts`)

`ARPG_CHECKLISTS` (line 22) and `ARPG_QUICK_ACTIONS` are declared as plain `Record<string, ChecklistItem[]>` and `Record<string, QuickAction[]>` objects, then **referenced by the `SUB_MODULES` array** of `SubModuleDefinition` objects. The flat `SUB_MODULE_MAP` dictionary and `CATEGORY_MAP` are built from those arrays at module load time (lines 1217–1220).

Each `SubModuleDefinition` carries:

- `id: SubModuleId` — the slug
- `categoryId: CategoryId` — determines which sidebar group it appears in
- `checklist?: ChecklistItem[]` — ordered steps, each with `{ id, label, description, prompt }` plus optional `dependsOn` (other checklist item IDs in the same module), `features` (feature names from registry 2), `visualCheck`, `lightingCheck`, `characterCheck` flags
- `quickActions: QuickAction[]` — one-shot prompts without progress tracking
- `knowledgeTips: KnowledgeTip[]` — shown as banners in `ModuleShell.tsx` (line 124) **and** injected into dispatch prompts via `formatKnowledgeTips()` (see Conventions below)
- `feasibilityRating?: 'strong' | 'moderate' | 'challenging'` — controls feasibility banner display

`CATEGORIES` (line 373) lists seven `CategoryDefinition` objects. The `core-engine` category's `subModules` array is intentionally left empty — its members are resolved by filtering `SUB_MODULES` against the private `CORE_ENGINE_IDS` array (line 434). All other categories enumerate their module IDs inline.

### 3. Registry 2 — Feature dependency graph (`src/lib/feature-definitions.ts`)

`MODULE_FEATURE_DEFINITIONS` (line 169) is a `PartialModuleMap<FeatureDefinition[]>` — not every module has entries. Each `FeatureDefinition` has:

- `featureName: string` — label unique within the module
- `category: string` — grouping label
- `dependsOn?: string[]` — references to either `'featureName'` (same module) or `'moduleId::featureName'` (cross-module)

`MODULE_PREREQUISITES` (line 7) is a separate, coarser graph at the **module** level (e.g., `arpg-combat` requires `arpg-gas` and `arpg-animation`). It drives `getRecommendedNextModules` and the `RoadmapChecklist` UI — it is **not** the same as the feature-level `dependsOn` graph.

`buildDependencyMap()` (line 452) converts `MODULE_FEATURE_DEFINITIONS` into a memoized `Map<featureKey, DependencyInfo>` where each key is `moduleId::featureName`. The result is static and memoized. `computeBlockers(depMap, statusMap)` (line 498) produces a fresh copy annotated with live `isBlocked / blockers` fields based on a caller-supplied `featureKey → status` map fetched from the API; a dependency is a blocker unless `isFeatureDone(status)` (`src/lib/feature-done.ts`: implemented OR improved - the one done rule the planner, topology and NBA share).

Two graph views render this data. The module-level `DependencyGraph` / `NexusView` (Evaluator → Dependencies / Nexus) draw **modules** as nodes with cross-module edges. Both — and the Overview roll-up's per-module blocked / cross-dependency counts — read ONE pure projection, `buildModuleTopology(statusMap, TOPOLOGY_COMPACT | TOPOLOGY_ROOMY)` in `src/lib/topology/moduleGraph.ts`: it returns nodes (done = `isFeatureDone`, i.e. implemented or improved; blocked; placed `cx/cy`), aggregated cross-module edges and a viewport sized from the placed cells. Placement keeps the curated `MODULE_POSITIONS` cells as fixed anchors and puts every other module in `MODULE_FEATURE_DEFINITIONS` into a band per category below them (`CATEGORIES` order, ids sorted), so a new module is placed automatically; canvases draw edges from node centres and zoom via `zoomViewBox`. Nexus's overlay layers (pattern success, critical findings, session activity) and its node deep-dive come from ONE pure projection, `projectNexusSignals(nodes, { runs, findings, patterns })` in `src/lib/evaluator/nexus-signals.ts`, over the durable tables — session_analytics module stats, the persisted deep-eval scans (via `scansToReports`; the deep-dive's Recommendations are the newest scan's findings) and the pattern-library dashboard — read by `NexusView/useNexusSignals.ts` (plus `?action=module` runs for the selected module's Recent CLI Sessions). Each source is a `SourceState` (loading / ready / failed): a failed source renders its layer toggle as unavailable + Retry, and a module with nothing measurable reads `null` (no badge), never 0. Nexus reads no `evaluatorStore`, no `moduleStore.moduleHistory` / `moduleHealth` and not the Pattern Library tab's `patterns` slice (source ratchet in `NexusView.signals.test.tsx`). The Dependencies tab is also where the backward walk becomes an action: `src/lib/topology/unblockFrontier.ts` computes a blocked feature's build frontier (`unblockFrontier` — the not-done prerequisites, across modules, whose own prerequisites are all done; visited-set walk), what one build clears (`previewUnblock` — blocked counts before/after plus newly ready features; `clearedEdgeIds` — the cross-module edges it stops blocking) and the global best next build (`criticalUnblocker` — ranked by the planner's `computeImpactScores` direct unblocks, ties by key). The tab shows that pick in a top callout and 'Build first' chips on each blocked feature row; hover previews the cleared edges, and Build resolves the `PlanItem` via `generatePlan` and dispatches `planItemToTask` through `useModuleCLI.execute` (the Implementation Plan path). The feature-level **Feature Constellation** (`src/lib/constellation/layout.ts` + `FeatureConstellation.tsx`, Evaluator → Constellation) lays out a **single** module's features in dependency layers (column = longest intra-module dependency chain), colors each node by its verified matrix status (`PLAN_STATUS_COLORS`), dims blocked paths and labels their blockers, and pulses the recommended next feature. The layout engine is presentation-free and pure — `layoutModuleConstellation(moduleId, statusMap)` returns positioned nodes/edges and `pickNextFeature` selects an unblocked, unbuilt, high-fan-out node — so it is fully unit-testable without a DOM.

The Evaluator's **Features** tab (`CrossModuleFeatureDashboard`) turns its heatmap counts into the same action. The module name opens the module. Each non-zero status cell opens `CellDrillPanel` in place, below the grid, and does not navigate; a second click or Esc closes it. The panel's rows come from `drillCell(statusMap, moduleId, status, generatePlan(statusMap))` in `src/lib/evaluator/feature-cell-drill.ts`, a pure projection. It lists the module's features with that status. A feature with no status row counts as 'unknown', and a status row with no definition is kept as `untracked`. Each row is `ready` (with its `PlanItem` as `buildItem`), `blocked` (with `unmetDeps` and `frontier = unblockFrontier(...)`), `done` or `untracked`. Rows are ordered ready, then blocked, then by impact desc and feature name. The bottom 'Buildable now' card is `buildableNow(plan, 8)`: ready, not-done items across modules, by impact. It replaced the old 'Most Missing Features' ranking by cross-module name overlap, where 222 of 231 names exist in one module only. Every Build on that tab (a ready row, a 'Build first' chip or a Buildable-now row) is an explicit click into `usePlanDispatch({ sessionKey: 'features-drill' })`. It is one CLI session, and the buttons are disabled while it runs. The header, rows and footer share `HEATMAP_GRID_TEMPLATE` (one track per `STATUS_KEYS` entry).

The Evaluator's **Conflicts** tab (`CrossModuleOverlapPanel`) reads `analyzeOverlaps()` (`src/lib/overlap-detection.ts`; a pair where one feature directly `dependsOn` the other is a declared edge and is not reported) as pairs of **twins**: most are one feature name defined in two modules, each with its own matrix row. `classifyTwin(pair, statusMap)` in `src/lib/evaluator/overlap-twins.ts` (pure, read-only, keyed `moduleId::featureName`) reads both statuses through `isFeatureDone` and returns `diverged` (one done; `reviewKeys` = the lagging twin), `unreviewed` (a side with no row or `unknown`), `agreed-open` or `agreed-done`; `orderTwins` puts divergence first, then similarity desc. The panel reads `useFeatureStatuses()`: each row carries a status dot per twin and a kind badge, the summary a Diverged count, and 'Review in <module>' dispatches `TaskFactory.featureReview(module, label, [thatFeatureDef], ...)` through one `useModuleCLI` session (`overlap-twin-review`) on click only, disabled while it runs; a confirmed landing calls `invalidateFeatureData()` so the row re-classifies. The overlap read is a `SourceState`: a failure renders the error + Retry, never 'No Overlaps Detected'; a failed status read renders 'Twin statuses unavailable' + Retry and leaves every twin unclassified (no dots, no review).

### 4. The NBA Engine (`src/lib/nba-engine.ts`)

`computeNBA(moduleId, featureStatusMap?)` is the primary consumer of registries 1 and 2. For each uncompleted checklist item it produces an `NBARecommendation` with a 0–100 composite score built from five weighted dimensions:

| Dimension | Weight | Source |
|-----------|--------|--------|
| urgency | 30 | Feature dependency fan-out (how many features this item unblocks) |
| successProbability | 25 | Pattern library match + module task-history success rate |
| impact | 20 | Dependency fan-out (duplicate of urgency factor, different coefficient) |
| recency | 15 | Evaluator scan recommendations for this module |
| readiness | 10 | Whether all `dependsOn` deps are satisfied in `depMap` |

Checklist items are matched to `FeatureDefinition` entries by fuzzy label-word matching (line 119–122). If no match, the item is treated as unblocked with readiness = 70 % of max.

The breakdown is no longer opaque to users: `RoadmapChecklist`'s NBA banner renders an `NBAScoreBar` under the top recommendation, projecting the `ScoreBreakdown` (via the pure `nba-breakdown.ts`) into a width-weighted segmented bar with a plain-language legend on hover/focus. Since the five weights sum to 100, each factor's points double as its percent width.

### 5. Registry 3 — Evaluator prompts (`src/lib/evaluator/module-eval-prompts.ts`)

`EVAL_PASSES` (line 18) defines the standard four-pass sequence: `ground-truth → structure → quality → performance`. One module (`arpg-combat`) also has a fifth `combat-trace` pass defined in `getPassesForModule`.

`MODULE_CONTEXTS` (line 70) maps each `moduleId` to a `ModuleEvalContext` with `focus`, `structureChecks`, `qualityChecks`, `performanceChecks`, and an optional `tracePass`. Modules without an entry in `MODULE_CONTEXTS` receive generic pass descriptions.

`buildEvalPrompt(params)` (line 346) assembles the full prompt string from the context + a shared `FINDING_SCHEMA` that instructs the model to return a JSON array of findings with `{ category, severity, file, line, description, suggestedFix, effort }`.

#### Running a scan (server job)

A deep eval runs **server-side**, never in the tab. **`src/lib/evaluator/deep-eval-job.ts`** holds one job per project on `globalThis`, behind **`/api/evaluator/deep-eval`**: POST `{ projectPath, projectName, ueVersion, moduleIds }` starts it and answers `{ scanId, job }` (409 while one is already running for that project), GET `?project=<path>` returns the job snapshot (`status`, `progress`, `result`), and DELETE `?project=` cancels it: every in-flight CLI execution is killed with `abortExecution`, then the run settles with the honest partial result (unfinished modules are failed, never evaluated). `useDeepEvalResults` starts a job only from the Run buttons, polls on `UI_TIMEOUTS.pollInterval`, and on mount **reattaches** to a job already running for the project without starting one. When the job settles, its result goes through the unchanged `applyScanResult` (diff, merge, `/api/evaluator/results`) exactly once. A job that settled while no tab was attached is not applied by a later mount.

- **`deep-eval-engine.ts`** is transport-free: `runDeepEval` takes an injected `executePass(prompt, projectPath, signal, cell)`. The job's default executor spawns each pass with cli-service `startExecution` with the same model pin and spend attribution the claude-terminal query route gives its spawns (`resolveDispatchModelChoice` with the `judge-content` class, `attribution.taskType: 'deep-eval'`). It collects `text` events and settles on `result` or `error`. Tests inject a fake, so the orchestration runs at zero model cost. The engine used to POST `{ prompt, cwd }` from the browser to `/api/claude-terminal/query`, which requires `projectPath`, so every pass answered 400.
- **A pass that says nothing parseable is unmeasured, not clean.** `parseFindingsStrict` (finding-collector) returns `Result<EvalFinding[], 'unparseable-output'>`: `[]` is a clean pass, while output with no JSON findings array fails the pass. A thrown executor error fails it as `cli-error: <message>`. The result carries `passStatuses` and `passErrors` per module, and the results banner names each failed module's reason (or `not finished (...)` for passes a cancel cut short).
- **Per-pass persistence and resume.** **`deep-eval-pass-ledger.ts`** is an additive `deep_eval_passes` table with one row per finished (scan, module, pass), written as each pass ends (`onPassEnd`). A job started with an existing `scanId` replays the passes the ledger holds as `done` and re-runs the rest, and it still reports findings in (module, pass) order. Nothing else reads the table. `evaluator_results` is unchanged and still written only by the tab through `/api/evaluator/results`.

#### Regression diff (new-since-last-scan)

`DeepEvalResults` diffs each fresh scan against the previous one so regressions stand out (the SonarQube "New Code" / GitHub code-scanning model), instead of re-triaging the whole backlog every run:

- **`src/lib/evaluator/finding-collector.ts`** exposes `fingerprintFinding(f, { includeLine })`. Within-scan dedup keys on the line-inclusive fingerprint; cross-scan diffing uses the **line-insensitive** form so a finding that merely shifts lines reads as *persisting*, not one resolved + one new.
- **`src/lib/evaluator/regression-diff.ts`** (pure) — `diffScans(previous, current, { scopeModuleIds })` tags every current finding `new`/`persisting` and reports prior findings now absent as `resolved`, with a per-severity `summary`. `scopeModuleIds` restricts the comparison to the modules actually re-evaluated (a single-module re-eval won't mark other modules resolved). `mergeBaseline(...)` builds the next stored baseline, replacing re-evaluated modules and keeping untouched ones.
- **`src/stores/deepEvalStore.ts`** caches the single most-recent scan's findings (localStorage `pof-deep-eval`) as the fast diff baseline. The **durable** history is the `evaluator_results` table (**`src/lib/evaluator/evaluator-results-db.ts`**, one row per completed scan) written/read via **`/api/evaluator/results`** (POST a scan; GET `?limit=N` history / `?latest=1` baseline). `useDeepEvalResults` persists every completed scan and hydrates its baseline from the DB when localStorage is empty, so regressions survive re-scans, reloads, and browser switches.
- **`src/lib/evaluator/scan-delta.ts`** (pure) — `deriveScanDeltas(scans)` turns the scan history into a per-scan NEW/RESOLVED/PERSISTING trend (each scan diffed against the immediately-older one, scoped to the modules it re-evaluated, using the same fingerprint `diffScans`). Served by **`/api/evaluator/deltas`** and consumed by the **Game Director's Regression Tracker** (`RegressionTrackerView` → `EvaluatorScanDeltas`) as an additional, clearly-labelled *code-quality* source alongside its playtest/crash sessions — this is the wiring behind the context-map's "results drive the Game Director's quality regression tracking" claim. Empty history renders nothing (the tracker is unchanged when no scans exist).
- **`src/lib/evaluator/scan-report.ts`** (pure) — `scansToReports(scans)` projects the same history into the `EvaluatorReport` series the **Scanner tab's Project Health dashboard** renders, read through `useScannerFeed` (`GET /api/evaluator/results?limit=10&project=<path>`). Health is 100 minus `SEVERITY_PENALTY` per finding (critical 20 / high 8 / medium 3 / low 1, floored at 0); coverage accumulates oldest→newest, a module never evaluated is **absent** (not 0), and the overall is the mean of the defined scores with "scored M of N modules" beside it. `regressionAlertsFromScans` derives its alerts per module from `deriveScanDeltas` (no second score-threshold rule), and Fix sends `generateFixPlan(finding, ctx)` on the finding's own module. The dashboard no longer reads the writer-less `evaluatorStore`; an empty history opens Deep Eval, a failed load shows an error with Retry.
- **`src/lib/evaluator/git-attribution.ts`** + **`/api/evaluator/git-attribution`** reuse the codebase-archeologist `git log` approach to attribute each NEW finding to the commit(s) that touched its file since the previous scan (`--since` = prior scan time). The pure `parseAttributionLog` is unit-tested; the git-spawning `attributeFilesSince` is server-only.
- **`RegressionBanner.tsx`** renders the compact `+N critical / −M resolved / persisting` summary above the tree plus a **New / All** view toggle; the view defaults to *New issues* whenever a baseline exists and something new appeared.

### Judge-verdict layer in the evaluator

The AI content-judge fleet's verdicts (`judge_verdicts` table, `src/lib/status/judge-verdicts-db.ts`) surface inside the evaluator, not only on the /status map:

- **Verdicts tab** (`src/components/modules/evaluator/JudgeVerdictsView/`) — read-only rollup of all verdicts grouped by catalog worst-first (pure `verdictRollup.ts`), each opening an EvidenceModal-grade findings detail. Data via `GET /api/judge-verdicts`; never re-grades. **Headline counts match acceptance:** `GET` attaches each row's server-computed `provenance` (`judgeBridge.verdictProvenance` against the artifact on record — only the server holds those artifacts, so a client cannot derive it), and totals/averages come from the STANDING subset only (`isStanding`, `@/lib/judge/verdictStanding` — the same set `CONDEMNING_PROVENANCE` acceptance acts on). Before this the tab counted every stored row, so a superseded-rubric fail and a fail bound to content the step no longer holds both inflated a fail count and dragged an average the acceptance layer itself did not hold. Non-standing rows are **not hidden** — they are evidence: they stay in the list after the standing ones, carrying the same `VERDICT: CURRENT / STALE / UNVERIFIED / SUPERSEDED` vocabulary the lab's `ProvenanceStrip` uses, so the distinction is legible without opening the modal, and the header states how many were left out and why. The modal adds rubric standing (`rubric v2 (current v3)`) and the `contentHash` binding.
- **Score trend across re-judges (2026-07-29)** — a re-judge used to DESTROY the record of what the judge previously said: `judge_verdicts` keys one row per `(catalog, entity, step, judge)`, so the second run overwrote the first, and the single question a quality loop exists to answer — *did my fix actually improve this?* — could not be answered from the data, even though the loop's own campaigns re-judge repeatedly. `judge-verdicts-db.ts` now also writes an **append-only** `judge_verdict_history` table (additive second table via the migration-latch pattern; `judge_verdicts` is untouched, so `bridgeJudgeVerdict` still sees exactly ONE applicable verdict per judge class and acceptance is provably unchanged — pinned by `src/__tests__/lib/judge/verdictHistory.test.ts`). Both writes share one transaction and one `judged_at`. **Retention is bounded:** the newest `VERDICT_HISTORY_LIMIT` (20) judgments per step + judge class, pruned inside the same transaction; the current verdict is never pruned. On an existing database the verdicts already on record are seeded as each trend's first point (one-time, only when the table did not exist). Read via `GET /api/judge-verdicts/history?catalogId&entityId&step[&judge]`, projected by the pure `@/lib/judge/verdictTrend.ts` (`buildVerdictTrend` → points oldest-first, delta, direction, best/worst, and `sameContentAsPrevious` from the content bindings) and shown in the verdict detail modal by `VerdictScoreTrend` — a shared `ChartPanel` `bars` row per judgment plus a one-line summary. A rise between two judgments of the SAME `contentHash` is labelled judge variance, not a fix. Evidence only: no module under `src/lib/catalog/acceptance/` reads the log (structurally asserted).
- **Per-dimension scores** — `judge_verdicts` carries an additive nullable `dimensions` JSON column (the judge's per-dimension 0-100 rubric scores; `scripts/judge-run.ts` persists them). The shared **`ui/DimensionScoreBars.tsx`** (MeterBar-backed) renders them in BOTH the /status `EvidenceModal` and the evaluator's verdict detail — one renderer, no drift. Legacy rows without dimensions render unchanged.
- **/status evidence modal = entity ledger** — a map cell aggregates every entity of a step, so the modal (`status/EvidenceModal.tsx`) opens on the entity HOLDING THE STEP DOWN, not API index 0. Pure `src/lib/status/cellLedger.ts` runs the map's own `buildSwimlane` over one entity at a time (as `scripts/personal-loop/truth.ts` `readCell` does) and orders blocked, then lowest rung, then entityId; `evidenceFor` keeps verdict, attribution and dimensions paired per entity so a verdict can never sit over another entity's proof. Rows come from the shared blob-free `useStatusArtifacts` read and verdicts from `useStatusVerdicts` (passed down by `PipelinesView` — the modal fetches no verdicts); proof is ONE entity's `GET /api/pipeline-artifacts?catalogId&entityId`. A failed verdict read marks every row `unavailable` (UNKNOWN, never "no judgment"). Each row hands off to Item Focus (`onFocusEntity` → `/status?entity=cat:id`). Display-only: the ledger never feeds a grade (`src/__tests__/lib/status/cellLedger.test.ts` guard).
- **Judged-content health term** — `src/lib/evaluator/combined-health.ts`: when a module has verdicts, the composite becomes 30% quality + **25% judged content** + 20% dep + 15% coverage + 10% activity; without verdicts the historical 40/30/20/10 output is byte-identical (test-asserted). Catalog→module attribution goes through the explicit `CATALOG_MODULE` map; unmapped catalogs are excluded, never guessed. The shared `judgeDiscrepancy` rule flags "matrix reads healthy but judges failed the content" and drives the `QualityDiscrepancyBanner` on the Quality tab (renders nothing when signals agree).
- **Health lifts** — `src/lib/evaluator/health-lifts.ts`: because the composite is linear, a dimension forfeits exactly weight × (100 − value) points; `rankModuleLifts` / `topProjectLifts` price each dimension with the weight set the breakdown used (`healthWeightsFor`: base vs `WEIGHTS_WITH_JUDGE`) and attach a structural remedy (`review` → `TaskFactory.featureReview` through `useModuleCLI`, `open-tab` → Dependencies / Quality tab, `open-module` → `navigateToModule`). The Summary tab's Module Health cells open that lift plan and a "biggest levers" strip sits under the gauge; a review dispatches on click only, never on render.

## Game Director: external playtest ingestion

Every Game Director session used to come from the in-repo dev fixture (`src/lib/game-director-sim.ts`, route action `simulate`), stamped `source: 'simulated'`. **`src/lib/game-director/external-ingest.ts`** is the first path that produces an `external` session. Its run-record shape is the **harness run state pair** — `game-plan.json` (a `GamePlan`) plus `progress.json` (a `ProgressEntry[]`) — the only run-record shape with real, committed on-disk examples in this repo (`.harness-dzin/`, `.harness-content/`, `.harness-ui/`, `.harness-dzin-full/`). `buildIngestPlan()` is the pure mapping; `ingestExternalPlaytest(record, { writer })` drives an injected `DirectorWriter` (the five external-writer route actions), bound to the DB by `src/lib/game-director/db-writer.ts` and reached over HTTP through the route action `ingest-external`.

Run it with `node scripts/game-director/ingest-run.mjs <state-dir-or-run.json> [--origin http://localhost:3001] [--project <path>] [--dry-run]`. The script holds no mapping logic — it reads the files and POSTs `{ action: 'ingest-external', run }`, so the contract has exactly one implementation. **A live UE run was NOT performed when this path was built:** it was developed and verified against the committed harness records above and against fixtures derived from them.

**The in-app door: import a stored harness run.** Every orchestrated run is already stored in `harness_runs` (`plan_json` + `progress_json`, `src/lib/harness-runs-db.ts`). New Session → *From a harness run* (`NewSessionPanel/HarnessRunImport.tsx`) lists the active project's runs (`GET ?action=harness-runs&projectId=`, joined on `normalizeProjectId` because `harness_runs.project_path` is stored raw), previews one (`POST preview-harness-run` → `previewHarnessRun` in `src/lib/game-director/harness-import.ts`: the import's own `validateRunRecord` + `buildIngestPlan` projected to build id / findings / unrouted / refused / score; writes nothing) and imports only on click (`POST ingest-harness-run` → `importHarnessRun` → `ingestExternalPlaytest` + the route's `completeSessionPipeline`; the module then opens the SessionDetail). The run id is stamped into `config.harnessRunId` (optional `PlaytestConfig` key, no schema change; `getSessionByHarnessRun` looks it up via `json_extract`): a re-import is **409** naming the session that holds the run (`details.sessionId`), and the lookup + claim are one synchronous step behind a per-run single-flight guard, so two concurrent imports write one session. Dedupe covers this door only — `ingest-external` / the script carry no run identity and are unchanged. Guards: `__tests__/lib/game-director-harness-import.test.ts`, `__tests__/api/game-director-harness-import.test.tsx`.

The mapping is built to the ai-registry subject `game-production/craft-judgment/playtest-signal-to-defect`. The session contract is a gate, not a suggestion: a record with no build identity, no declared coverage or no timeline is **refused with its reason** and writes nothing — an empty session stamped `external` would read as a build that was measured and found clean. Findings carry an evidence pointer (build + area + iteration to re-run) or are refused; frequency is always stated with its denominator and never multiplied into severity; the harness's own narration is quarantined in `suggestedFix` as interpretation and never reaches the router; and a module with no finding-category route becomes a **named `unrouted` entry** (announced on the timeline) rather than being swept into a default bucket. Coverage, screenshots and playtime are written `null` ("not measured"), and confidence stays unscored — a gate verdict is evidence, not a 0-100 score. `SessionDetail` will not offer the simulator on an `external` session, since re-simulating would overwrite measured findings and restamp the row `simulated`.

### Game Director ↔ feature matrix (priority systems + routing write-back)

**`src/lib/game-director/matrix-routing.ts`** closes the loop between the Director and the feature matrix, in both directions. `derivePrioritySystems(aggregates)` seeds the New Session form's `prioritySystems` (previously typed "from feature matrix" and hardcoded `[]`) from `/api/feature-matrix/aggregate` — the modules with `missing` rows first, then the lowest average quality, each chip stating its reason ("3 missing, avg quality 41") and each one togglable. A module with **no rows** under the project is never offered: unreviewed is not weak. The selection and the project ride on the session in `PlaytestConfig` (`prioritySystems`, the new `projectId`).

On completion — `simulate`, `ingest-external` and the external writer's `complete` all call `completeSessionPipeline` in the route, whose first step is `routeSessionFindings` — `routeFindingsToMatrix` appends one queue line per owning module to that module's weakest matrix row (missing first, then lowest quality; an *unscored* row is not treated as the lowest). The line is **appended, never overwriting** the operator's own text, is stamped `[game-director <sessionId>]` so a re-complete is a no-op, and names its provenance in words — a `simulated` session's line says plainly that no build was launched, so a canned finding can never read as an observed gap. Routing uses `findingRouteModuleId` (`findingFix.ts`), which returns `null` rather than the polish catch-all: a finding nothing owns, or a module holding no row under this project, is reported as a named `unrouted` miss instead of being filed under a default bucket. Every outcome, including "nothing was written and here is why" (an unscoped write-back is **refused**, not widened to the legacy rows), lands as a timeline event that `SessionDetail` renders verbatim under the provenance banner. Reads and writes go through injected deps bound to `feature-matrix-db` by `createDbMatrixRoutingDeps()`; the write path declares itself `source: 'unknown'` because a routed queue line is not a review.

### Game Director regression tracking: session time, analyzed on completion

**One session clock.** `game-director-db.ts` exports `SESSION_CHRONOLOGY_ASC` / `_DESC` (`datetime(created_at), rowid`) and `sessionChronology()`; `listSessions`, `getDirectorStats().recentSessions`, `getHealthTrend` and the regression tracker all order by it. `created_at` has one-second resolution, so `rowid` breaks same-second ties by insertion order. `getHealthTrend(limit)` selects the NEWEST `limit` completed sessions and returns them oldest → newest (it used to keep the oldest `limit`, so the chart froze after session 30).

**Status moves only forward in session time.** `processSession` (`src/lib/regression-tracker.ts`) stamps the session `regression_analyzed_at` (additive nullable column on `game_director_sessions`, so deleting a session takes its mark with it) and picks its pass with `analysisMode(chronology, sessionId)`: a session at or after the newest analyzed one runs `forward` (occurrences, status transitions, the scoped fixed-sweep, alerts); an older one runs `backfill` (occurrences and counts only, new fingerprints start `open`, no sweep, no alert). `RegressionReport.mode` says which ran. The guarantee is deliberately bounded: no analysis order can mark `fixed` a fingerprint the newest analyzed session contains, and a session older than the newest analyzed one only backfills occurrences. It is not order-independence — S1{X} S2{} S3{X} analyzed S1,S3,S2 ends `open`, chronologically it ends `regressed`. The superset-of-categories sweep rule is unchanged.

**Analyzed on completion.** The route's `completeSessionPipeline(sessionId, source)` is the one set of completion side-effects, called by `simulate`, `ingest-external` and the external writer's `complete`: `routeSessionFindings` (matrix routing, above), then `analyzeSessionRegressions`, best-effort and disclosed as a timeline event (`Regression analysis: N new, N regressed, N newly fixed.`, a `(backfill — …)` variant, or `Regression analysis FAILED — …`). `GET /api/regression-tracker?action=sessions` returns `RegressionSessionOption` (`analyzed`, `analysisMode`); `RegressionTrackerView` marks analyzed sessions in the picker and labels the button **Backfill** for an older session. Guards: `__tests__/lib/regression-chronology.test.ts`, `__tests__/api/game-director-completion-pipeline.test.ts`, `__tests__/lib/regression-sweep-scope.test.ts`.

**Two separate dependency graphs coexist.** `MODULE_PREREQUISITES` is module-to-module (coarse, drives `RoadmapChecklist` and `getRecommendedNextModules`). `MODULE_FEATURE_DEFINITIONS[moduleId][].dependsOn` is feature-to-feature (fine, drives the NBA engine via `buildDependencyMap` / `computeBlockers`). **`ChecklistItem.dependsOn` is intra-module only.** These are checklist item IDs (e.g., `'ae-1'`), not feature keys. Cross-module ordering is expressed in `MODULE_PREREQUISITES` (module level) or `FeatureDefinition.dependsOn` (feature level), not in checklist `dependsOn`.

**Blueprint "Write to Project" reviews an overwrite by member, not by line; a loss needs an acknowledgement and merge is a clicked CLI task.** The dry-run modal (`blueprint-transpiler/BlueprintTranspilerView/WriteToProjectButton.tsx`) runs the pure `src/lib/blueprint-transpiler/overwrite-review.ts` over the plan's on-disk `before` and generated `after`: `reviewOverwrite(header, source, className)` parses both headers with the shared `parseHeader` and scans both `.cpp` files for `<Class>::Name(...) {` definitions (class name regex-escaped; qualified calls excluded), returning `new-file | no-loss | loses-members` with `lost` UPROPERTY/UFUNCTION members (signature + specifiers), `changed` members whose specifier names were dropped (e.g. `ReplicatedUsing`), `lostDefinitions`, and a stated `boundary` (plain declarations, types, specifier values and bodies are not compared). Membership, not location: a reordered/re-commented header is `no-loss` even when the line diff shows red. `OverwriteReview.tsx` renders the verdict above the line diff (nothing for a new file); `overwriteConfirmGate(review, acknowledged)` disables **Confirm write** on `loses-members` until **Overwrite and drop N members** is ticked (reset on every dry run). **Merge via Claude** dispatches `TaskFactory.askClaude('blueprint-transpiler', buildOverwriteMergePrompt(review, target))` through `useModuleCLI` and closes the modal — the app itself writes nothing on that path. The server write route is unchanged. Guards: `__tests__/lib/blueprint-transpiler/overwrite-review.test.ts`, `__tests__/components/blueprint-overwrite-review.test.tsx` (ack gate; merge never sends `confirm: true`).

**Blueprint codegen and the Semantic Diff are two projections of one C++ member model.** `src/lib/blueprint-cpp-surface.ts` `deriveCppSurface(asset)` is the single record of what a Blueprint becomes: class name/prefix, each UPROPERTY with its specifiers, every UFUNCTION tagged by origin (`bp-function` / `custom-event` / `onrep-handler`), resolved event overrides (unknown and duplicate events kept as lists) and the replication block (`replication-scaffolder.ts`). It also holds `resolveEventOverride`/`deriveFunctionSignature` (re-exported from codegen) and `isEditorExposed` (the Edit* family only; `BlueprintReadWrite` exposes to graphs, not the Details panel). `generateCppFromBlueprint` renders the header and source from it; `computeSemanticDiff` compares the parsed header (`parseHeader`) against it. So diffing the transpiler's own output reports nothing, a header missing a custom event is `add`/`event`, a `ReplicatedUsing` that names an undeclared OnRep handler is an `add`/`function` conflict (UHT rejects it), and only UFUNCTIONs outside the surface count as C++-only. Custom-event and OnRep parameter lists are checked for presence only. Guards: `__tests__/lib/blueprint-cpp-surface.test.ts` (round-trip is clean for the sample and a replicated door; UFUNCTIONs re-parsed from the emitted header equal the surface set; emitted C++ is byte-identical to the pre-refactor output) and `__tests__/lib/blueprint-semantic-diff.test.ts`.

**Blueprint transpile fidelity is counted per node, and the residue is a worklist one click from each stub.** The node walker (`generateNodeLogic`, optional `ledger` param) records a disposition for every node it reaches: `emitted` (became a statement), `consumed` (a VariableGet an emitted statement reads), `structural` (event / function entry — the member itself), `refused` (left a `// TODO` stub, with the walker's reason); `generateCppFromBlueprint` refuses unknown and duplicate events and marks every node never visited `unreached`, naming the node in front of it (behind a refused Branch or unknown event, a pure value feeding one, or disconnected). The result carries it as the additive `TranspileResult.nodeLedger`. `describeTranspileFidelity` counts that ledger — structural nodes are out of the denominator, unreached nodes are never "translated" (`'0 of 7 nodes translated · 2 refused · 5 never reached'`); only a payload without a ledger falls back to the old warning-derived count (`perNode: false`). Every walker stub is stamped `(node <id>)` on one line (newlines in names/defaults are folded). `src/lib/blueprint-transpiler/residue.ts` is pure: `locateStub(code, nodeId)` returns the stub's 1-based line; `buildResidue(result)` lists refused entries (with `file`/`line`; an unknown event points at its header `// TODO: Override for <name>`, found by name because that pinned line carries no id) then unreached ones (`line: null`). In `TranspilePane` the fidelity chip toggles `ResidueList.tsx`; clicking a refused row switches to that file's tab and passes `focusLine` to the shared `CodeViewer`, which marks that `.line` `data-focused="true"` and scrolls it into view. `CodeViewer` keys its highlighted HTML by the code+lang it was made from, so a viewer handed new code re-highlights instead of keeping the previous file's body (`focusLine` is optional; without it nothing is marked). Guards: `__tests__/lib/blueprint-transpiler/residue.test.ts`, `__tests__/lib/blueprint-cpp-codegen.test.ts` (`describeTranspileFidelity`, stub stamp), `__tests__/components/code-viewer.test.tsx` (re-highlight on new code; focusLine; stable code highlighted once).

**The Progression Rewards tab puts reward pacing on the clock.** `sub_progression/_shared/rewardPacing.ts` is the ONE pacing model, and it is pure. `PacingModel` is `{ baseXp, exponent, maxLevel, xpPerMinAtL1, rateGrowth }`. XP per level comes from `calculateXpForLevel`, the one XP law. The earn rate `xpPerMin(L) = xpPerMinAtL1 * L^rateGrowth` is a stated assumption (`DEFAULT_RATE`, 100 XP/min at L1, growth 1), and the panel prints it beside the figures. The kernel exports `minutesPerLevel`, `cumulativeMinutes`, `daysToMax(model, minutesPerDay)`, `rewardSchedule(rewards)` (co-level rewards grouped, ascending), `pacingTimeline` (hours from start, hours since the previous unlock, `drought` = gap > 2x the median gap, `clump` = more than one reward on a level), `gapCV`, `evenSpacingSuggestion` (group k of n goes to the level whose cumulative time is nearest k/n of time-to-max; levels are strictly increasing and the last is the cap) and `respaceSchedule`. The tab root holds `baseXp`/`curveExp` and one `rewardGroups` state. `TimeToLevelEstimator` derives its stat tiles and the casual/hardcore days-to-max from the live curve. Its bars are relative to the longest playstyle, so hardcore is 12.5% of casual. `LevelUpRewardPreview` is controlled (`schedule`, `onScheduleChange`). It renders one row per level group, keyed by level, with `+Xh after previous`, Drought/Clump badges, the gap CV, and the "Apply even spacing" and "Shipped levels" actions. `XpTableGenerator` takes the same `schedule`. `generateProgressionTable` puts every reward at a level into that row's one `UnlockReward` cell (`unlockRewardCell`, joined by `; `). `progressionToCSV` quotes the cell and doubles any embedded `"`, so `DT_ProgressionCurve` keeps 50 unique RowNames and 7 fields per row and still imports against `FProgressionCurveRow`. Before this, `.find` exported 8 of 15 unlocks. Guards: `__tests__/components/progression/rewardPacing.test.ts`, `xpTableRewards.test.ts`, `TimeToLevelEstimator.test.tsx`, `LevelUpRewardPreview.test.tsx`.

**The Progression Curves tab reads one curve model.** `sub_progression/_shared/curveModel.ts` (pure) derives every curve figure on the Curves tab from `calculateXpForLevel` and the `rewardPacing` clock. `curveTotals(base, exp)` returns `cumulativeXp[L]` (the exported table's `XPTotal`), `totalXp` at the cap and `hoursToMax` (`cumulativeMinutes / 60`, the Rewards tab's "Hours to max"). `curveDelta(snapshot, live)` returns the `COMPARISON_LEVELS` rows, both totals and `hoursDiff`; `xpOverlaySeries(base, exp)` is the overlay's XP series. `CurveDeltaSummary` takes only the two parameter pairs and shows "Total XP to L50" and "Time to max (h)" with the rate basis printed. **The Curves tab tunes by pace.** `sub_progression/_shared/curveFit.ts` (pure) turns milestone-hour targets into slider values. `fitCurveToTargets(targets)` searches all 1334 reachable slider settings (`BASE_XP_RANGE` x `CURVE_EXP_RANGE`, 46 x 29) and minimises the sum of `ln(achieved / target)^2`, ties going to the lower base. Achieved hours are `cumulativeMinutes(pacingModel(base, exp))[L] / 60`, the Rewards-tab clock, never a separate rate. The result carries one residual per target, the worst miss, `limitedBy` (the slider bounds the best point sits on) and a verdict: `fit` (every target within 10%), `range` (the best point sits on a slider bound, so the targets want a value past it) or `shape` (an interior best that still misses: no curve of this power-law family meets the targets, so change the targets or the formula, not the knobs). Two targets are nearly always met; a third is what exposes a shape failure (L10 1h / L25 2h / L50 20h gives 110 / 1.85 with L25 at +98%, `shape`). `parsePaceTargets` validates the panel's text rows as a `Result`. The tab root holds its curve state in one `useReducer(curveTuningReducer)` (`live`, `snapshot`, `compareMode`, `previewing`) instead of five `useState`s. `toggleCompare` snapshots the live curve as before. `previewFit` opens compare with the pre-fit curve as the snapshot, and only `apply` or `revert` (explicit clicks) end a preview; toggling compare does nothing while one is open. `PaceTargetsPanel` sits under Curve Parameters. Its rows default to L10 and the cap, prefilled with the current curve's hours, and it lists target vs achieved per row, the verdict, and Apply fit / Revert. During a preview `MainChartArea` labels the split pane Current / Fitted, and `CurveParametersPanel` locks Compare; it also prints Hours to L50 from `curveTotals`. Nothing is persisted, and the pinned catalog curve does not move. Guards: `__tests__/components/progression/curveFit.test.ts`, `PaceTargetsPanel.test.tsx`.

**Item DNA has ONE rules table: `src/lib/item-dna/rules.ts`.** It owns `RARITY_ORDER` / `rarityIndex`, `ITEM_TYPES`, `AFFIX_COUNT_RANGES` (`affixCountRange`, `describeAffixCount`), level scaling (`scaleByLevel`, `describeLevelScale`), `GOD_ROLL_THRESHOLD`, the dominant axis (`dominantGene` / `dominantAxis` = the argmax weight, the one definition the roller, the coherence score and evolution share) and evolution (`EVOLUTION_TIERS` `{ tier, xp, label, bonus }`, `tierForXP`, `nextTierXP`, the cumulative `tierBonus(tier)`, `EVOLUTION_ROLL_BONUS_PER_TIER`). `rolling-engine.ts` applies these rules and `defaults.ts` re-exports `ITEM_TYPES` / `ITEM_RARITIES` from it; the `sub_inventory/dna-genome` tabs (Editor, Roller, Evolution, Monte Carlo) only render them, so a tuning edit is one line that moves the engine and every caption together. **The affix workbench has ONE crafting kernel: `sub_loot/affix-workbench/craftingKernel.ts`.** It is pure and seeded (`Rng = () => number`; tests pass `createRNG` from `@/lib/seeded-rng`, the hooks pass `Math.random`) and owns the minRarity predicate (`isEligible` / `eligiblePool`, the only copy: the pool panel, `detectArchetypes` and the Breakpoint rarity filter all call it), the weighted pick, `instantiateAffix`, `rollItem`, `scaledMagnitude(affix, itemLevel)` and the reducer `applyCraft(state, action, ctx) -> { state, entry } | { state, entry: null, refused }` over `CraftState { affixes, wallet, totalSpent, craftCount, log }`. A refusal (no open slot, nothing unlocked, no prefixes to lock) charges and logs nothing; a failed success roll is a paid attempt. Locks are the per-affix `locked` flags and the PRE/SUF badges are `deriveLocks(affixes)`, never stored, so a badge cannot claim a lock reforge will not honour; reforge keeps exactly the locked affixes and consumes the locks, Divine Roll and Annul & Exalt leave locked affixes alone. `useCraftingEngine` / `useAffixWorkbench` only hold state and write the kernel's result back. `generateExportCode(base, affixes, itemLevel)` takes the slider item level and emits magnitudes as `cppFloat(scaledMagnitude(...))`, the same value `/api/ue5-inject-item` receives. The `_orphan` panels (SynergyDetector, ArchetypeSuggestionGrid) import the workbench `data.ts`; their former 343-line `_orphan/data.ts` fork is gone. Pinned by `__tests__/components/core-engine/affix-crafting-kernel.test.ts`.

**Price this item: `sub_loot/affix-workbench/craftGoal.ts`.** The hand-built affix set is a craft goal (`{ rarity, targetTags }`). `priceCraftGoal({ rarity, targetTags, start, wallet, runs, rng, maxSteps, step })` is a seeded Monte Carlo that steps the kernel's `applyCraft` on a COPY of the wallet, following one policy, `nextCraftAction(state, goal)`: null when every target is held, augment while a slot is open, and on a full item unlock locked strays, lock a side made only of targets (when an Eternal Lock is affordable), else remove_add. It returns `{ status: 'priced', successRate, spend: Record<CurrencyId, { mean, p50, p90 }> | null, crafts: { p50, p90 } | null, failures: { walletExhausted, stepCap, stuck } }`. Spend and crafts cover the runs that reached the goal (cost-to-obtain within this wallet) and are null when none did. An unreachable goal (a target whose minRarity is above the base, more targets than the rarity has slots, an unknown tag) returns `{ status: 'unreachable', reason }` without stepping once. `useAffixWorkbench().priceCurrentItem()` prices from an empty base with `defaultWallet()`, 400 runs and a fixed seed (the same item always gets the same price). It never touches the live wallet, craft log or craft count. `goalReport` is exposed only while the item and base it priced are current. `CraftGoalPanel` (under the preview card) shows an unreachable goal's reason, or the success % and Forging Potential mean/p90 as the headline cost. Pinned by `__tests__/components/core-engine/affix-craft-goal.test.ts`, including the closed-form case: one affordable augment on an Uncommon base gives 0.85 x w(T) / W(Uncommon pool) within 0.03.
